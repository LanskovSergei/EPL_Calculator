# Калькулятор ГСМ — бэкенд (неделя 1: алгоритм + API)

FastAPI-бэкенд для расчёта путевых листов. Логика 1:1 портирована из
`src/calc.ts` фронтенда — числа сходятся между клиентом и сервером.

## Запуск

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Swagger-документация: http://localhost:8000/docs

## Эндпоинты

- `GET /api/health` — проверка живости.
- `POST /api/calculate` — принимает `ВходныеДанные` (см. `app/schemas.py`,
  поля названы так же, как в `src/types.ts` фронта), возвращает
  `РезультатРасчёта` (список путевых листов + предупреждения + сводку расхода).

## Валидация (`app/schemas.py`)

Помимо типов и обязательности полей, на уровне pydantic-модели `ВходныеДанные`
проверяется:

- `периодПо` не раньше `периодС`;
- для спецтехники обязателен ручной средний расход;
- список водителей не пуст;
- для междугородного/международного сообщения указан срок рейса;
- рабочие дни водителей и даты заправок попадают в расчётный период.

При ошибке валидации FastAPI возвращает `422` с человекочитаемым списком
сообщений в `detail` (см. `app/main.py: validation_exception_handler`).

## Структура

```
backend/
├─ requirements.txt
└─ app/
   ├─ main.py      # FastAPI app, CORS, обработчик ошибок валидации
   ├─ routes.py     # POST /api/calculate, GET /api/health
   ├─ schemas.py    # pydantic-модели входа/выхода
   └─ calc.py       # чистый движок расчёта (порт src/calc.ts)
```

## CORS

Разрешённые origin'ы задаются переменной окружения `ALLOWED_ORIGINS`
(через запятую). По умолчанию — `http://localhost:5173` (Vite dev-сервер).

## Геокодинг (Шаг 2.1/3, впрок)

`app/geocoding.py` — клиент Яндекс.Геокодера. Работает по ключу
`YANDEX_GEOCODER_API_KEY` из `.env` (скопируй `.env.example` → `.env` и
впиши ключ). Пока ключа нет — `is_configured()` вернёт `False`, а
`geocode_address()` тихо вернёт `None`, ничего не ломая: расчёт путевых
листов не зависит от геокодинга.

Получить ключ: https://developer.tech.yandex.ru/ → сервис «Геокодер».

Тесты (`tests/test_geocoding.py`) работают на моках HTTP — реальный ключ
для них не нужен.

## Форма №3 (легковой) — печать (Шаг 2.2)

- `POST /api/form3/excel` — Excel (`.xlsx`), один лист на каждый путевой лист.
- `POST /api/form3/pdf` — PDF, одна страница на каждый путевой лист.

Тело запроса — `ЗапросФормыПЛ`: `расчёт` (те же поля, что у `/api/calculate`)
+ `организация`/`тс`/`водитель`/`прицеп` (документные реквизиты) +
`типПеревозки` + `поля` (чекбоксы, что печатать — остальное пользователь
дозаполнит на бланке вручную, см. ТЗ Шаг 2.2). Только для `типТС: легковой`
(грузовой — форма №4-с, следующий шаг), при попытке грузового — 422.

PDF использует шрифт DejaVu Sans (`app/fonts/`) — кириллица корректно
отображается (в отличие от встроенных PDF-шрифтов reportlab).

## Форма №4-с (грузовой) — печать (Шаг 2.2, продолжение)

- `POST /api/form4c/excel`, `POST /api/form4c/pdf` — аналогично форме №3,
  но с прицепами (до 2) и грузовыми реквизитами (`ездки`: пункты
  погрузки/разгрузки, номер ТТН, грузоотправитель/получатель). Тело —
  `ЗапросФормы4С`. Только для `типТС: грузовой`.

## Валидация чеков через ОФД (впрок)

`app/receipt_validation.py` — как и геокодинг, сделан впрок: парсинг
QR-кода чека (`parse_qr`) работает уже сейчас без токена, а обращение к
сервису проверки (`validate_receipt`) включается токеном
`OFD_CHECK_TOKEN` в `.env`. Пока токена нет — валидация просто
пропускается (`is_configured() == False`), это осознанно совпадает с
ответом заказчика: «на первом этапе проверку подлинности можно не
проводить». Актуальной валидация станет на шаге формирования Акта на
списание ГСМ.

## Маршрут (Шаг 2.1, MVP)

`ВходныеДанные.адресСтоянки` (точка отправления/возврата) и
`Заправка.адрес` (адрес АЗС из чека) — опциональные поля. Если заданы,
каждый `ПутевойЛист.маршрут` содержит текстовый список:
стоянка → АЗС по чекам этой смены в хронологическом порядке → стоянка.
Валидация «АЗС вписывается в маршрут» — следующий шаг, использует
`geocoding.haversine_km` для грубой проверки расстояний.
