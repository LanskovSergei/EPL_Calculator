# Неделя 4: форма №4-с (грузовой) + валидация чеков через ОФД

## Что сделано

### Генерация путевого листа форма №4-с (грузовой)

- **Схема** (`app/schemas.py`): `ЗапросФормы4С` — как и `ЗапросФормыПЛ`
  для формы №3, но:
  - `прицепы: List[ДанныеПрицепа]` — до 2 прицепов (лимит формы);
  - `ездки: List[ЕздкаГруза]` — пункт погрузки/разгрузки, наименование
    груза, номер ТТН, грузоотправитель/грузополучатель, вес;
  - валидация — только `типТС: грузовой`, для легкового — 422 (форма №3).
  - MVP-упрощение: грузовые реквизиты общие на расчётный период, а не
    привязаны к конкретному путевому листу (калькулятор пока не хранит
    «эта заправка — от этой ездки»). Печатаются на каждом ПЛ как задание
    водителю. Если понадобится точная привязка ездок к датам — можно
    добавить поле `дата` в `ЕздкаГруза` и матчить по датам ПЛ.

- **`app/forms_4c.py`** — `generate_form4c_excel()` / `generate_form4c_pdf()`,
  переиспользуют шрифт и стили из `app/forms.py` (форма №3), добавляют
  блок «Задание водителю (груз)» с ТТН и прицепами.

- **Эндпоинты**: `POST /api/form4c/excel`, `POST /api/form4c/pdf`.

- **Тесты** (`tests/test_forms_4c.py`, 7 шт. + 3 в `test_api.py`):
  количество листов/страниц, наличие ключевых реквизитов (номер ТТН,
  гос. номер прицепа, наименование груза), отказ для легкового ТС, лимит
  «не более 2 прицепов».

### Валидация чеков через ОФД

Ответ заказчика на этот счёт: *«На первом этапе проверку подлинности
можно не проводить... Актуальной валидация станет на этапе Акта на
списание ГСМ»*. Поэтому — по аналогии с геокодингом (неделя 3) — сделал
модуль **впрок**, не блокирующий основной расчёт:

- **`app/receipt_validation.py`**:
  - `parse_qr(qr)` — разбирает стандартную строку QR-кода чека ФНС
    (`t=...&s=...&fn=...&i=...&fp=...&n=...`) в реквизиты. Работает уже
    сейчас, без какого-либо токена.
  - `validate_receipt(req)` — обращается к сервису проверки чеков
    (например, proverkacheka.com); включается токеном `OFD_CHECK_TOKEN`
    в `.env`. Без токена — тихо возвращает `None` («проверка
    недоступна»), ничего не ломает.
  - `extract_fuel_volume_liters(payload)` — пытается вытащить объём
    топлива из детализации чека (для будущей сверки с введённым вручную
    значением).
  - `ReceiptParseError` / `ReceiptValidationError` — раздельные
    исключения для «битый QR» и «сервис недоступен/ошибся».

- **Тесты** (`tests/test_receipt_validation.py`, 13 шт.): парсинг QR
  (валидный, с секундами, с `?` в начале, отсутствующее поле, битая
  дата/сумма), поведение без токена, успешная/неуспешная проверка и
  сетевая ошибка — всё на моках `httpx.MockTransport`, реальный токен не
  нужен. Извлечение объёма топлива из позиций чека.

Итого тестов в проекте: **91**, все зелёные.

## Как проверить

```bash
cd backend
pip install -r requirements.txt
pytest -v
```

Пример тела для `/api/form4c/*` — см. `tests/test_forms_4c.py::make_form_request`
или `tests/test_api.py::form4c_payload`.

## Не входит в этот шаг

- Реальное обращение к ОФД (нужен токен) и подключение
  `extract_fuel_volume_liters` к основному расчёту — когда появится
  токен и будет решено, нужна ли сверка «чек говорит N литров, а
  пользователь ввёл M» уже на этапе Шага 1.1/1.2, или это остаётся на
  этапе Акта, как и планировалось изначально.
- Интеграция с 1С — по плану, неделя 5.
